Written by The Clogger from the Exploiter run of 2026-11-08 (which tested `main` @ `8bf79e4`).

## 1. Summary

- **8 actionable findings** (1 high, 5 medium, 2 low) plus 4 info/attempted-failed items, which need no fix.
- **Re-verified against current code:**
  - 5 are still open: SSRF, track poisoning, yt-dlp orphans, ffmpeg orphans, SoundCloud log injection.
  - 1 is partly fixed: JWT. The algorithm is now pinned, but `exp` is still not required.
  - 2 are fixed on this branch: dependencies and Tauri CSP/allowlist.
  - 1 sub-claim is a false positive: the Google-callback half of the log-injection finding.
- **Highest priority:** `soundcloud-cursor-ssrf-token-exfil`. This is a one-function change to `buildUrl`. It is still exploitable, and it leaks the SoundCloud OAuth tokens. Size S.
- **Second:** the yt-dlp and ffmpeg orphan-process fixes, which share a root cause (nothing reacts when the client disconnects). One `res.on('close')` guard in the controllers plus a cap on background transcodes in `transcode.js`. Both size S.
- **Rough total effort:** about 1 to 1.5 days. The SSRF, log-injection, JWT and both DoS fixes take about 3 to 4 hours together. The per-user track metadata change (M) takes most of the rest.

## 3. Prioritized fix list

### 3.1 `soundcloud-cursor-ssrf-token-exfil`: SSRF + OAuth token exfiltration via the search cursor

Severity **high**. Status **confirmed, still open**.

**Fix:** `controllers/soundcloud/client.js`, `buildUrl()` (lines 226-243). The off-host check only runs when the string matches `/^https?:\/\//i`. Instead, always resolve the value against the base URL and then check the origin:

```js
function buildUrl(pathOrUrl, query) {
    const url = new URL(pathOrUrl, API_BASE);
    if (url.origin !== API_BASE) {
        throw new SoundCloudError('Refusing to follow a URL outside the SoundCloud API', { status: 400, code: 'BAD_CURSOR' });
    }
    // ...query loop unchanged
}
```

Why this is enough:
- `apiRequest` and `fetchCollection` both call `buildUrl`. So this one change covers client-supplied cursors and any `next_href` the server receives.
- Checked results for the proposed function:
  - Rejected: `http:127.0.0.1:4999/x`, `http:/h/x`, `" http://h/x"`, `"ht\ttp://h/x"`, `//h/x`, `\\h/x`, `/\h/x`, `file:`, `data:`, `https://api.soundcloud.com@evil`, `https://api.soundcloud.com.evil`, `http://api.soundcloud.com`.
  - Accepted: `/tracks`, `/me/likes/tracks`, `https://api.soundcloud.com/...?cursor=`, `HTTPS://API.SOUNDCLOUD.COM/...`.

Optional second layer: in `soundcloudController.searchTracks` (lines 218-254), return 400 for any cursor that does not start with `` `${client.API_BASE}/` ``.

**Verify:**
- In `tests/soundcloud.test.js`, extend `'refuses to follow a cursor that points outside the API host'` to loop over the bypass strings above. Expect `BAD_CURSOR` and no call to `fetchMock`.
- In `tests/soundcloudRoutes.test.js`, add `GET /api/soundcloud/search?q=x&cursor=http:127.0.0.1:4999/x`. Expect 400 and no fetch.
- The existing pagination tests (`next_href` on `api.soundcloud.com`) must still pass.

**Size:** S.

**Risk:** none known. SoundCloud's `next_href` is always on `api.soundcloud.com`, and the old code already rejected other absolute origins.

### 3.2 `ytdlp-stream-orphan-no-timeout`: yt-dlp has no timeout and is not killed on disconnect

Severity **medium**. Status **confirmed, still open**.

**Fix:** `controllers/YouTubeController.js`, in `streamTrack` (line 35) and `getDuration` (line 62):
- Pass a timeout, the same way `controllers/soundcloud/ytdlp.js` (`EXEC_TIMEOUT_MS`) and `services/ytdlp.js` do.
- Keep the child handle and kill it when the response closes.

```js
const RESOLVE_TIMEOUT_MS = 60 * 1000;
// streamTrack
let clientGone = false;
const child = execFile(ytDlpPath, args, { timeout: RESOLVE_TIMEOUT_MS }, (error, stdout) => {
    if (clientGone) return;            // nobody to stream to: do not spawn ffmpeg
    // ...existing body unchanged
});
res.on('close', () => { clientGone = true; child.kill('SIGKILL'); });
```

Use the same pattern in `getDuration`; there the `clientGone` check is optional.

Use `res` `'close'` rather than `req` `'close'`. It fires when the connection drops, and also after a normal finish. Killing a child that has already exited does nothing, so the normal finish case is harmless.

The `clientGone` guard also fixes a related bug. If the client leaves during yt-dlp resolution, `streamTranscoded` currently still spawns ffmpeg. Its `req.on('close')` listener is then registered after `'close'` has already fired, so that ffmpeg is never reaped, even on the `seek>0` path.

Same root cause on the SoundCloud side, `controllers/soundcloudController.js` `streamTrack` (lines 307-344):
- Register a `res.on('close')` flag before the `await withFallback(...)`, and return before `streamTranscoded` if the client has gone.
- Optionally let `soundcloud/ytdlp.js` `runner.exec` accept a `signal`, which `execFile` supports, so the 60 s resolve can be aborted too.

**Verify:**
- Add a jest test that uses `jest.mock('child_process')` so `execFile` returns `{ kill: jest.fn() }` and never calls back.
- Fire `request(app).get('/stream?videoId=dQw4w9WgXcQ').timeout(50)` and catch the abort.
- Assert that `kill` was called and that `execFile`'s third argument has `timeout`.
- Manual check: repeat the Exploiter's 12-request stub test and expect `pgrep -fc yt-dlp` to return 0 after about 1 s.

**Size:** S.

**Risk:** a legitimately slow yt-dlp resolve longer than 60 s now fails with `TRACK_UNAVAILABLE`, which is better than hanging.

### 3.3 `media-endpoints-unauthenticated-transcode-dos`: orphaned cacheable ffmpeg transcodes

Severity **medium**. Status **confirmed, still open** (exposure reduced).

The loopback bind (`server.js:12`) removes LAN attackers. However, any web page the user visits can still hit `http://127.0.0.1:3000/stream` through an `<audio>` or `<img>` tag. Those no-cors GETs carry no `Origin`, and `app.js:36` allows them. Meanwhile `transcode.js` `streamTranscoded` (lines 209-218) still lets every `seek=0` ffmpeg run after disconnect, bounded only by `MAX_TRANSCODE_MS` (10 min).

**Fix:** `controllers/transcode.js`, `streamTranscoded`. Allow only a small number of orphaned cache-filling transcodes, and kill the rest:

```js
const MAX_BACKGROUND_TRANSCODES = 2;
let backgroundTranscodes = 0;
// inside streamTranscoded
let orphaned = false;
req.on('close', () => {
    ffmpegProcess.stdout.unpipe(res);
    if (finished) return;
    if (fileStream && backgroundTranscodes < MAX_BACKGROUND_TRANSCODES) {
        orphaned = true;
        backgroundTranscodes++;
        return;                        // let this one finish into the cache
    }
    ffmpegProcess.kill('SIGKILL');
});
ffmpegProcess.on('close', (code) => {
    if (orphaned) backgroundTranscodes--;
    // ...existing body: non-zero exit already unlinks the .part
});
```

Together with 3.2's `clientGone` guard, an attacker who disconnects at once can keep at most 2 ffmpeg processes alive, instead of one per request.

Optional: also put a global cap on concurrent transcodes (for example 4) and return `503` above it.

**Verify:**
- In `tests/cache.test.js` or a new test, mock `spawn` to return an EventEmitter-based fake process with `kill: jest.fn()`.
- Start 5 cacheable transcodes with fake `req`/`res` emitters and emit `'close'` on every `req`.
- Assert exactly 3 `kill('SIGKILL')` calls.
- Emit `'close'` with code `null` on the killed processes and assert their `.part` files are gone.

**Size:** S.

**Risk:** a user who skips tracks quickly gets fewer warm-cache entries. The cap of 2 is a guess; tune it if needed.

### 3.4 `shared-track-metadata-poisoning`: first writer controls shared title/artist/thumbnail

Severity **medium**. Status **confirmed, still open**.

The relevant code:
- `historyController.logHistory` (lines 22-25) and `playlistController.addTrackToPlaylist` (lines 161-164) still `INSERT OR IGNORE` into `tracks`, with no length or URL checks.
- `getHistory` (lines 54-67) and `getCustomPlaylistTracks` (lines 186-194) read the shared row.

**Fix, step 1 (S): validate input.** Add one small helper, `services/trackMeta.js` exporting `cleanTrackMeta({ title, artist, thumbnail })`, and use it in both handlers:

```js
function cleanTrackMeta({ title, artist, thumbnail }) {
    if (typeof title !== 'string' || !title.trim() || title.length > 300) return { error: 'Invalid title' };
    if (artist != null && (typeof artist !== 'string' || artist.length > 200)) return { error: 'Invalid artist' };
    let image = null;
    if (typeof thumbnail === 'string' && thumbnail.length <= 2048) {
        try { const u = new URL(thumbnail); if (u.protocol === 'https:') image = u.toString(); } catch { /* drop */ }
    }
    return { title: title.trim(), artist: artist ? artist.trim() : null, thumbnail: image };
}
```

A bad thumbnail is stored as `null` rather than rejected, so no client flow breaks. Also cap `trackId`/`externalId` at 128 chars.

**Fix, step 2 (M): per-user display metadata.**
- In `config/db.js`, after the `CREATE TABLE` block, add nullable `title`, `artist` and `thumbnail` columns to `history` and `playlist_tracks`. Use the existing `PRAGMA table_info` + `ALTER TABLE ... ADD COLUMN` pattern already used for `user_connections.expires_at`.
- Write the user's own (validated) values on those rows.
- Read them with a legacy fallback, for example `CASE WHEN h.title IS NULL THEN t.title ELSE h.title END AS title`, and the same for `artist` and `thumbnail`. Do not use a per-column `COALESCE`, or a user's null artist falls back to another user's value.
- After this, `tracks` only maps `(source_id, external_id)` to an id.

**Verify:**
- A new `tests/history.test.js` test against an in-memory SQLite DB (`initDB` with `:memory:`, or a temp file). User 1 logs `dQw4w9WgXcQ` with metadata X, user 2 logs it with Y. Each user's `GET /history` and playlist tracks return only their own values.
- A 900 000-char title returns 400.
- A `javascript:` or `http://` thumbnail is stored as null.
- The existing `tests/playlist.test.js` mocks must still pass. They need one more `mockDb` expectation per new column; update their argument indexes.

**Size:** M (step 1 alone is S, and it fixes the 900 KB and tracking-pixel parts).

**Risk:**
- Schema migration, but additive and nullable.
- Rows poisoned before the fix keep showing the shared value until the user plays the track again. A one-off `UPDATE tracks SET thumbnail = NULL WHERE thumbnail NOT LIKE 'https://%'` is an optional cleanup.

### 3.6 `jwt-verify-no-algorithm-pin`: algorithm now pinned, `exp` still optional

Severity **low**. Status **partially fixed on branch, residual open**.

What changed in `08bbae5`:

- Line 23 rejects non-session purposes.
- Line 24 requires an integer `userId`.

Re-verified behaviour:

**Fix:** in `requireAuth`, right after `jwt.verify`:

```js
if (typeof payload.exp !== 'number') throw new Error('no expiry');
```

## 4. Broader improvements (not flagged by the Exploiter)

1. **Authenticate the media endpoints with a short-lived media token (M).**
   - `/stream` and `/duration` (`app.js:109-110`) stay unauthenticated because `<audio>` cannot send a Bearer header. The loopback bind does not stop a drive-by web page from loading `http://127.0.0.1:3000/stream?...`.
   - In SoundCloud API mode, every unauthenticated `/stream` also spends the app token's 15 000 plays / 24 h quota (`soundcloudController.streamTrack`).
   - Suggested design:
     - Issue a `jwt.sign({ userId, purpose: 'media' }, secret, { expiresIn: '1h', algorithm: 'HS256' })` from an authenticated endpoint.
     - The client appends `&t=` to the `<audio>` URL.
     - A small middleware verifies the token with `purpose === 'media'`.
   - This follows the purpose-separation pattern from `08bbae5`.
2. **Global transcode concurrency cap (S).** Keep a module-level `activeTranscodes` count in `transcode.js`. Above it (for example 4), return 503 `{ error: 'Server busy' }` before spawning ffmpeg.
3. **Validate the custom playlist thumbnail too (S).** `playlistController.createCustomPlaylist` (line 109) stores any string as `thumbnail`. It is the user's own data, but reusing `cleanTrackMeta`'s URL check keeps the rules consistent.
4. **Tighten Tauri `img-src` (S, after 3.4).** `img-src 'self' data: https:` lets any https image load in the webview. After per-user metadata lands, consider `https://i.ytimg.com https://*.sndcdn.com` (confirm the CDN hosts the clients actually return first).
5. **Lower the CI audit gate (S).** The production tree is at 0, so `--audit-level=moderate` costs nothing today and catches moderate advisories (`qs`, `ip-address`, etc.) early.
6. **Regression tests for the defended classes (S).** Turn the Exploiter's "attempted-failed" probes into fixtures so a future refactor cannot silently regress them: SQLi literals, `assertPlaylistOwnership` 404s, `../` and `--exec` videoIds, and evil/`null` Origin returning 403.
7. **Explicit algorithm on the OAuth state sign (S).** In `authController.getGoogleAuthUrl` (line 18), pass `algorithm: 'HS256'` to `jwt.sign` to match the verify side. It already defaults to HS256; this is for readability and symmetry.
