## 3. Prioritized fix list

### media-endpoints-unauthenticated-transcode-dos -- medium, confirmed

- **Fix**: `app.js` (route registration for `/stream`/`/duration`, lines
  109-110) and a new `middleware/requireMediaToken.js`, paired with a new
  `GET /api/media-token` endpoint protected by the existing `requireAuth`.
  Mint a short-lived (~60-120s), single-purpose JWT -- `purpose: 'media'`,
  `userId`, `source`, `id` -- the same way `controllers/authController.js`
  mints a `purpose: 'google_oauth'` token and `middleware/requireAuth.js`
  rejects anything whose `purpose` isn't `'session'`. Require this token as a
  query parameter on `/stream` and `/duration` (the `<audio>` element can set
  `src` with a query string but cannot send a header), and verify it matches
  the request's own `source`/`id` so a captured token can't be replayed
  against a different track.

  ```js
  // middleware/requireMediaToken.js (new)
  module.exports = (req, res, next) => {
      try {
          const payload = jwt.verify(req.query.mtoken, process.env.JWT_SECRET, { algorithms: ['HS256'] });
          if (payload.purpose !== 'media') throw new Error('wrong token purpose');
          if (payload.source !== String(req.query.source || 'youtube')) throw new Error('track mismatch');
          if (payload.id !== req.query.videoId) throw new Error('track mismatch');
          req.userId = payload.userId;
          next();
      } catch {
          res.status(401).json({ error: 'Invalid or expired media token.' });
      }
  };
  ```

  ```js
  // app.js
  app.get('/api/media-token', requireAuth, mediaTokenController.issue); // new
  app.get('/stream', mediaLimiter, requireMediaToken, streamingController.handleStream);
  app.get('/duration', mediaLimiter, requireMediaToken, streamingController.handleDuration);
  ```

  Client-side: `client/src/context/MusicContext.jsx` (`loadAudio`, and the
  `seek`/preload call sites at lines 67, 224, 282) already holds
  `localStorage.getItem('authToken')`; have it `fetch('/api/media-token?...',
  { headers: { Authorization: ... } })` and splice the returned `mtoken` into
  the `streamUrl`/`duration` query string before setting `audioRef.current.src`
  or calling `fetch`.

- **Verify**: add a case to `tests/securityFixes.test.js` (or a new
  `tests/mediaToken.test.js` in the same supertest + `jwt.sign` style already
  used there): `GET /stream`/`/duration` with no `mtoken`, an expired one, a
  `purpose: 'session'` one, and a token minted for a different `videoId` all
  return 401; a token minted via `requireAuth` + `/api/media-token` for the
  matching `videoId`/`source` reaches the existing 400/502 provider-resolve
  path exactly as today. `tests/transcodeLimit.test.js` should keep passing
  unmodified (it exercises `streamTranscoded` directly, below this layer).
- **Size**: M -- touches one route file, two new small files, and the one
  client hook that constructs stream/duration URLs in four places.
- **Risk / follow-up**: the token rides in a URL query string, so it can leak
  via browser history, `Referer` headers to any third-party resource the page
  also loads, or server/proxy access logs -- keep the TTL short (the fix above
  uses ~60-120s) and avoid logging full query strings for these two routes.
  This does not fully stop a same-origin, already-logged-in malicious script
  (e.g. an XSS bug) from minting its own tokens, but that is a different,
  broader threat model (XSS) than the one this finding is about (an arbitrary
  third-party page with no access to the victim's session).

### cors-origin-restriction-info -- info, info (minor hardening, not a vulnerability)

- **Fix**: `app.js`, central error handler (lines 130-137). Add two more
  branches before the generic 500, mirroring the existing
  `err.message === 'Not allowed by CORS'` check: map `express.json()`'s
  oversized-body error (`err.type === 'entity.too.large'`) to 413, and its
  malformed-JSON error (`err instanceof SyntaxError && 'body' in err`) to 400.

  ```js
  app.use((err, req, res, next) => {
      if (err && err.message === 'Not allowed by CORS') {
          return res.status(403).json({ error: 'Origin not allowed' });
      }
      if (err && err.type === 'entity.too.large') {
          return res.status(413).json({ error: 'Request body too large' });
      }
      if (err instanceof SyntaxError && 'body' in err) {
          return res.status(400).json({ error: 'Malformed JSON body' });
      }
      console.error('Unhandled error:', err);
      if (res.headersSent) return;
      res.status(500).json({ error: 'Internal server error' });
  });
  ```

- **Verify**: re-run the Exploiter's manual checks (malformed JSON body to
  `POST /history`, a 2MB body) and assert 400/413 instead of 500; no stack
  trace or internal detail should still reach the client either way.
- **Size**: S.
- **Risk / follow-up**: none -- purely a response-code accuracy improvement,
  no new information is exposed in either the old or new behaviour.

- **`/api/health` detail vs. auth-only gate**: it's behind `requireAuth`
  (good, per the comment in `app.js`), but any authenticated user of the
  multi-tenant local server can see yt-dlp/ffmpeg binary versions for every
  other user's install. Not a cross-user data leak (no per-user data in the
  payload per `services/health.js`), so no finding was filed, just a note for
  if this server is ever deployed multi-tenant rather than single-user-local.
- **Dependency hygiene**: the dev-only moderate/high findings
  (`client`'s `vite`/`source-map-js`/`zod`/`minimatch`, root's `pkg`/`jest`
  transitive deps) are out of the shipped app, but are worth a routine
  `npm audit fix`/version bump in a maintenance pass since they add no risk
  to defer indefinitely.
- **Test coverage gap**: there is no existing test that boots `app.js` and
  asserts `/stream`/`/duration` return something other than 401 without
  credentials today (the current "no-auth-by-design" behaviour is only
  implicit). Once the media-token fix lands, the new test described above
  closes this gap; until then, consider a documentation note in `app.js`'s
  existing comment (line 107-108) making explicit that this is a known,
  tracked gap rather than an oversight, so a future contributor doesn't
  "fix" it inconsistently.
