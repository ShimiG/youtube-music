# Security Review -- 2026-11-09

Weekly authorized security review of the Music Manager app (Node/Express API +
React client). This is the follow-up to the 2026-11-08 review; the fixes
landed on `stage-3-stabilise` (see commit "Stage 3 security: fix Exploiter
findings from 2026-11-08") were re-tested fresh rather than assumed fixed.

## 1. Summary

- Tested: JWT forgery/expiry/algorithm pinning, cross-user IDOR on playlists
  and history, SQL injection on every DB-backed endpoint, path traversal and
  argument injection on `/stream`/`/duration`, the SoundCloud search `cursor`
  SSRF/token-exfiltration primitive, OAuth callback log injection, CORS/origin
  handling, rate limiting, and error-handling/info-disclosure, plus a full
  `npm audit` (root + client, prod and dev) and a re-read of every file touched
  by last week's fixes.
- Of 12 recorded items: **1 confirmed** (unchanged, already known, partially
  mitigated), **0 potential**, **8 attempted-failed** (all defended, 7 of
  which are fixes from last week re-verified working), **3 info** (dependency
  audit clean, hardening notes).
- **Most urgent item**: `/stream` and `/duration` still take no authentication
  and no signed media token (`media-endpoints-unauthenticated-transcode-dos`).
  Last week's mitigation (capping abandoned cache-writing transcodes at 2) is
  confirmed working and stops unbounded orphan-process growth, but any web
  page a user's browser loads can still trigger real yt-dlp+ffmpeg work (and
  spend SoundCloud's play quota) against their own local server without a
  token, up to the 60/min per-IP limit.
- Every previously-confirmed finding from 2026-11-08 that was marked `fixed`
  was re-tested dynamically or by direct code-path probe this week and
  confirmed defended: SoundCloud cursor SSRF, shared-track metadata poisoning,
  yt-dlp orphan processes, production dependency vulnerabilities, OAuth error
  log injection, and JWT algorithm/expiry/purpose pinning.
- No new vulnerability classes were found this week; static review of every
  controller, middleware file and the SoundCloud client turned up no new
  `child_process`/path-traversal/SQL-concatenation issues beyond what was
  already tracked.

## 2. Assumptions

- Target: `http://127.0.0.1:3999` (`PORT=3999`, `HOST=127.0.0.1`), booted with
  a throwaway random 64-char hex `JWT_SECRET`, `YTDLP_AUTO_UPDATE=false`, and
  `SOUNDCLOUD_CLIENT_ID`/`SOUNDCLOUD_CLIENT_SECRET` left unset so the run stays
  fully offline (SoundCloud search/stream fall back to the yt-dlp provider).
- The sandbox only ships `bin/yt-dlp_macos` (no Linux yt-dlp binary) and no
  network egress to YouTube/SoundCloud is in scope anyway, so YouTube/SoundCloud
  `/stream`, `/duration` and `/api/soundcloud/search` calls fail immediately
  with `ENOENT`/`resolve_failed` rather than doing real work. This does not
  weaken the auth/validation/traversal tests (which fail closed before any
  process would spawn) but means the yt-dlp-orphan-process and background-
  transcode-cap findings are confirmed primarily by code review plus the
  project's own mocked unit tests (`tests/transcodeLimit.test.js`), not a live
  multi-minute process-counting reproduction as was done on the author's
  mac-based sandbox last week.
- SoundCloud "API mode" (official API with real `client_id`/`secret`) was not
  exercised live -- doing so would require a real SoundCloud OAuth app, which
  is a third-party service and out of scope. The SSRF/token-exfiltration
  finding is instead re-verified by calling the exported `buildUrl()` function
  in-process with the exact bypass payloads from last week and confirming each
  is now rejected, which is the authoritative fix location regardless of
  provider mode.
- Two throwaway local accounts were created via `POST /api/register`:
  `sec_alice_tmp` and `sec_bob_tmp`. Both, plus the SQLite DB, cache directory,
  and generated `.token-key`, were deleted at the end of the run; the server
  process was killed. `client/package-lock.json`, incidentally touched by
  `npm install`, was reverted.
- `client/` was `npm install`-ed to run its own `npm audit`; the client was not
  built or served, since the API surface under test is the Express server.

## 3. Confirmed vulnerabilities

### media-endpoints-unauthenticated-transcode-dos -- medium (unchanged from last week, partially mitigated)

- **Location**: `app.js:109-110` (routes registered with no `requireAuth`);
  `controllers/transcode.js:35-36, 160-259` (`streamTranscoded`,
  `MAX_BACKGROUND_TRANSCODES`).
- **Exploit**: `/stream` and `/duration` carry no `Authorization` requirement
  by design (the native `<audio>` element cannot send a Bearer header), and
  are reachable cross-origin: a request with no `Origin` header (which is what
  `<audio src=...>`/`<img src=...>` send) passes the CORS allowlist check in
  `app.js` unconditionally. `GET /stream?videoId=zzzzzzzzz01` with no
  `Authorization` header reached input validation and the provider-resolve
  path, returning a normal 400/502 rather than a 401, confirming the route
  requires no session. The only two protections on the live instance are (a)
  the 60-requests/minute `mediaLimiter` (per IP) and (b) the new
  `MAX_BACKGROUND_TRANSCODES = 2` cap that was added since last week, which
  correctly bounds how many *abandoned, cache-writing* transcodes may keep
  running after their client disconnects (verified via the project's own
  `tests/transcodeLimit.test.js`, which this run re-executed as part of the
  full 160-test suite: exactly `max` transcodes survive a mass-disconnect and
  the rest are `SIGKILL`'d). Neither protection stops a malicious web page
  from making a victim's browser spend up to 60 real transcodes per minute
  while the tabs stay open, or from spending SoundCloud's 15,000-plays/24h API
  quota on the user's behalf.
- **Impact**: Any third-party page the logged-in user's browser visits can
  silently drive CPU/ffmpeg/yt-dlp load and API quota on the user's own local
  server, up to the per-IP rate limit, with no consent step and no way for the
  server to distinguish this from the real player. This is a reduced-severity
  version of last week's finding (the unbounded background-process growth
  itself is fixed); what remains open is the lack of any authentication or
  short-lived signed media token on these two routes, which last week's
  `resolution` note already flagged as the follow-up item.

## 4. Potential weaknesses

None recorded this week beyond the confirmed item above.

## 5. Successfully defended

All of the following were actively tried against the live instance (or, where
noted, the exact code path) and the app defended correctly:

- **SoundCloud cursor SSRF / token exfiltration** (`soundcloud-cursor-ssrf-token-exfil`):
  every bypass form from last week (`http:127.0.0.1:4999/x`, `http:/127.0.0.1/x`,
  leading-whitespace `http://`, `//evil/x`, `\\evil/x`, `file://`, `data:`) now
  throws `BAD_CURSOR` from `buildUrl()` instead of resolving to an off-host
  URL; legitimate `/tracks/123` and `https://api.soundcloud.com/...` paths
  still work.
- **Shared track-metadata poisoning** (`shared-track-metadata-poisoning`): bob
  logging history for a track id does not change what alice sees for the same
  id in her own playlist/history reads; a 900,000-char title is now rejected
  outright (400) rather than silently truncated and stored.
- **yt-dlp orphan processes** (`ytdlp-stream-orphan-no-timeout`): code review
  confirms `runYtDlp()` now passes a 60s `timeout` and kills the child on
  client disconnect before any `ffmpeg` is spawned for a dead request.
- **JWT forgery and lifecycle** (`jwt-verify-no-algorithm-pin`): `alg=none`,
  5 guessed weak secrets, `HS512` with the real secret, an expired token, a
  token with no `exp` at all (the gap left open last week -- now closed), and
  a token with a foreign `purpose` claim were all rejected with 401.
- **Identity spoofing**: an `x-user-id` header has no effect on `req.userId`
  with or without a valid token from a different account.
- **IDOR on custom playlists / history**: bob could not read or write alice's
  playlist by id (`404 Playlist not found`); bob's own history/playlist
  listings stayed empty regardless of query-string or header tricks.
- **SQL injection**: parameterized queries throughout; `' OR '1'='1`-style
  playlist ids and login usernames were treated as literal values and matched
  nothing.
- **Path traversal / argument injection on `/stream`, `/duration`**:
  `../../etc/passwd`, URL-encoded traversal, NUL bytes, `-o/tmp/pwn`-style flag
  injection and `;id` were all rejected by the `videoId`/cache-key regexes
  before any process could spawn; `seek` and `source` are similarly validated.
- **OAuth callback log injection** (`oauth-error-log-injection`): a `%0A`-laden
  `error` parameter to `/auth/soundcloud/callback` is now sanitized to a single
  alnum/`.`/`_`/`-` token capped at 64 chars before logging; no forged log
  lines appeared.
- **CORS**: unknown origins and the literal string `null` get 403; only the
  configured allowlist (`http://localhost:5173` etc.) gets a matching
  `Access-Control-Allow-Origin`.
- **Rate limiting**: 21 rapid `POST /api/login` attempts produced 15x 401 then
  6x 429; 65 rapid `GET /duration` calls produced 13x 429, consistent with the
  20/15min and 60/min limiters respectively.
- **Error handling**: malformed JSON and an oversized (2MB, over the 1MB
  limit) request body both returned a generic `{"error":"Internal server
  error"}` with no stack trace to the client (the 500 status code is slightly
  imprecise for these cases -- see the info note below -- but nothing leaks).

## 6. Dependency and static findings

- **Root, production dependencies**: `npm audit --omit=dev` -> 0 vulnerabilities
  (critical/high/moderate/low/info all 0). Re-confirms the 2026-11-08 fix
  (body-parser, proxy-addr, undici, qs all upgraded via `overrides`).
- **Root, including dev dependencies**: 19 findings (0 critical/high, 16
  moderate, 3 low) -- all in build/test tooling (e.g. `pkg`/`jest` transitive
  deps), not shipped.
- **Client, production dependencies**: `npm audit --omit=dev` -> 0
  vulnerabilities. `client/package.json` `dependencies` is just
  `@tauri-apps/api`, `react`, `react-dom`.
- **Client, including dev dependencies**: 4 findings (1 moderate `minimatch`,
  3 high: `source-map-js`, `vite`'s `launch-editor`/CORS issues, `zod`) -- all
  under `devDependencies` (the Vite build toolchain), confirmed not present in
  the production dependency list and not part of the built/shipped app.
- **Static grep sweep**: re-checked every `child_process` call site
  (`controllers/transcode.js` spawn, `controllers/YouTubeController.js`
  execFile, `controllers/soundcloud/ytdlp.js` execFile) -- all pass argv arrays
  (no shell), all have a `timeout`, and user input only ever reaches a single
  positional argument whose value is independently validated (11-char YouTube
  id regex, numeric SoundCloud id regex) before the process is spawned.
  Re-checked every `path.join`/`path.resolve` call in `controllers/transcode.js`
  -- all resolve against `cacheDir`/`resolvedCacheDir` and re-verify the
  `startsWith(resolvedCacheDir + path.sep)` invariant. No SQL string
  concatenation found anywhere in the controllers; every query uses `?`
  placeholders.
- **Tauri hardening** (`tauri-csp-null-and-shell-allowlist`, build-time, not
  dynamically tested): `src-tauri/tauri.conf.json` now sets a strict CSP
  (`default-src 'self'` etc., no longer `null`) and the shell allowlist no
  longer includes `execute`; `open` is restricted to `^https://`.

## 7. Scope and safety

- All requests were sent to `127.0.0.1:3999`, a disposable instance of this
  repository's own code, started and stopped entirely within this run.
- No request was sent to any external host: `SOUNDCLOUD_CLIENT_ID`/`SECRET`
  were left unset so SoundCloud calls stay on the local yt-dlp fallback (which
  itself failed closed, since no Linux yt-dlp binary is bundled, rather than
  reaching soundcloud.com); Google OAuth was not exercised beyond its own
  input-validation code paths (no real `GOOGLE_CLIENT_ID`/`SECRET` configured,
  so no request to Google was possible or attempted).
- The only "network" traffic generated was to `127.0.0.1` (the app under
  test) and to `registry.npmjs.org` via the pre-configured proxy for
  `npm install`/`npm audit`, which is build tooling, not the target of the
  assessment.
- Two throwaway accounts (`sec_alice_tmp`, `sec_bob_tmp`) were created and
  used only against the local instance; the SQLite database, `cache/`
  directory and generated `.token-key` created by this run were deleted
  before finishing, and the server process was killed. No source file was
  modified to conduct testing (only environment variables were set for the
  disposable boot), and the one incidental `client/package-lock.json` change
  from `npm install` was reverted.
