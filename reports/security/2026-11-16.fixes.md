## 3. Prioritized fix list

### 3.1 `cloud-url-no-ssrf-guard` — medium — **confirmed**

**Location:** `services/cloud/client.js:27-45` (`normalizeUrl`) and `:66-92` (`request`);
called from `services/cloud/sync.js:80-102` (`checkCloudUrl`/`saveCloudUrl`), reached via
`PUT /api/cloud/url` in `controllers/cloudController.js:43-48` (owner-only route,
`app.js:177`).

Verified: `normalizeUrl()` only checks protocol shape — `https:` for any hostname, or
`http:` for the two literal hostnames `localhost`/`127.0.0.1` (a documented,
test-covered `wrangler dev` exception — see `tests/cloudSync.test.js:95-106`). It never
checks whether the resolved address is private, link-local, or a metadata-style address.
`request()` then calls global `fetch()` directly with no address check and no custom DNS
resolution. This matches the Exploiter's PoC (`PUT /api/cloud/url {"url":"http://127.0.0.1:3999"}`
→ `400 CLOUD_BAD_URL`, proving the server actually connected) and extends it: any
`https://` hostname or IP literal that is RFC1918/link-local/CGNAT/metadata-range (e.g.
`169.254.169.254`) would sail through `normalizeUrl` today, unlike `services/artworkColors.js`,
which blocks exactly these ranges via a `net.BlockList` (`isPublicAddress`, `checkUrl`,
`guardedLookup`) before ever connecting.

**Fix:** `services/cloud/client.js`, function `request()` (and a new small shared module):

1. Extract the blocklist + `isPublicAddress()` out of `services/artworkColors.js:59-80`
   into a new `services/netGuard.js`, and have `artworkColors.js` re-export them from
   there (`module.exports = { ...require('./netGuard'), ... }`) so
   `tests/artworkColors.test.js`'s existing `isPublicAddress`/`guardedLookup` imports keep
   working unchanged.
2. In `services/cloud/client.js`, add a guard called at the top of `request()`, before
   `http.fetch(...)`:

   ```js
   const dns = require('dns').promises;
   const net = require('net');
   const { isPublicAddress } = require('../netGuard');

   const DEV_LOOPBACK_HOSTS = new Set(['localhost', '127.0.0.1']); // unchanged wrangler-dev exception

   async function assertReachableHost(url) {
       if (DEV_LOOPBACK_HOSTS.has(url.hostname)) return;
       const literal = url.hostname.replace(/^\[|\]$/g, '');
       if (net.isIP(literal)) {
           if (!isPublicAddress(literal)) throw new CloudError('UNREACHABLE', 'The cloud service could not be reached.');
           return;
       }
       let addrs;
       try { addrs = await dns.lookup(url.hostname, { all: true }); }
       catch (err) { throw new CloudError('UNREACHABLE', 'The cloud service could not be reached.', 0, { cause: err }); }
       if (!addrs.length || !addrs.every((a) => isPublicAddress(a.address))) {
           throw new CloudError('UNREACHABLE', 'The cloud service could not be reached.');
       }
   }
   ```

   Call `await assertReachableHost(new URL(path, baseUrl))` at the start of `request()`,
   before the existing `http.fetch(...)` call.

**Verify:** add to `tests/cloudSync.test.js`: `saveCloudUrl(db, 'https://169.254.169.254')`
and `saveCloudUrl(db, 'https://10.1.2.3')` each reject with `CloudError` (`UNREACHABLE`);
`http://127.0.0.1:8787` and `http://localhost:8787` (the existing dev-loopback test cases
at line 97-98) must still pass unchanged; a DNS mock resolving a normal hostname to a
public address must still succeed (use the existing `fakeCloud`/mocked-fetch test harness,
stubbing `dns.lookup` the way `tests/artworkColors.test.js` stubs `runner.dnsLookup`).

**Size:** M (half a day) for the tier-1 fix above. One real risk/follow-up: this is a
check-then-connect guard, so it has a narrow DNS-rebinding window (a hostname that
resolves to a public address at check time and a private one moments later at connect
time) — the same class of bug `artworkColors.js` closes completely by pinning DNS
resolution to the actual connecting socket (`guardedLookup`/`downloadWith`, using core
`https.get(url, { lookup })` instead of `fetch()`). Doing the equivalent for cloud/client.js
means replacing global `fetch()` with core `https.request()`/`http.request()` end to end
(porting timeout, redirect-rejection, and body-size-cap logic) — a larger follow-up (**L**,
more than half a day) worth doing for full defense-in-depth, but not required to close the
concrete PoC and the metadata/RFC1918 risk the Exploiter demonstrated, since an attacker
able to run a DNS-rebinding attack against this path would need to already control the
owner account that can set the cloud URL in the first place.

### 3.2 `health-endpoint-any-authenticated-user` — low — **confirmed**

**Location:** `app.js:90-96` (route); `services/health.js:80-94` (`getHealth`); consumed by
`client/src/components/SystemPanel.jsx:22,61-73` and
`client/src/context/MusicContext.jsx:335-337`.

Verified: the route is `requireAuth` only, confirmed by reading `app.js:90-96` next to
`/api/system/log` (`requireAuth` + `settingsController.requireOwner`, `app.js:100`). Both
client call sites use `/api/health` for *every* logged-in account's own Settings → System
panel and for the "nothing can play" toast — not an owner-only feature — and
`README.md:255`/`docs/packaging.md:113` document it as login-only by design. So gating the
whole endpoint behind `requireOwner` (matching `/api/system/log`) would break a real,
documented, used feature for every non-owner account. The actual risk the Exploiter flagged
is narrower: exact binary **version strings** help pick a known exploit, not the
available/not-available fact itself.

**Fix:** `services/health.js`, function `getHealth()`:

```js
async function getHealth({ fresh = false, isOwner = false } = {}) {
    const [binaries, cache] = await Promise.all([probeBinaries(fresh), cacheUsage()]);
    const degraded = !binaries.ytDlp.available || !binaries.ffmpeg.available;
    const redact = (b) => isOwner ? b : { available: b.available, version: null, ...(b.startMs !== undefined ? {} : {}) };
    return {
        status: degraded ? 'degraded' : 'ok',
        version: pkg.version,
        node: isOwner ? process.version : null,
        uptimeSec: Math.round(process.uptime()),
        platform: process.platform,
        binaries: { ytDlp: redact(binaries.ytDlp), ffmpeg: redact(binaries.ffmpeg) },
        cache,
        log: { enabled: logFile.enabled(), file: `logs/${logFile.FILE_NAME}` }
    };
}
```

and in `app.js`'s `GET /api/health` handler, compute `isOwner` the same way
`controllers/cloudController.js:32-34` already does for cloud status:

```js
app.get('/api/health', requireAuth, async (req, res, next) => {
    try {
        const isOwner = await settings.isOwner(req.app.locals.db, req.userId);
        res.json(await getHealth({ fresh: req.query.fresh === '1', isOwner }));
    } catch (err) { next(err); }
});
```

(`settings` = `require('./services/appSettings')`, already imported by
`controllers/cloudController.js` and easy to require in `app.js` alongside the other
service imports.)

No client change is required: `SystemPanel.jsx:68` already renders
`found.version || 'Found'`, so a `null` version degrades to "Found" for non-owner accounts
instead of an exact version string; `platform` stays visible (needed for the mac install
hint) since it is not itself a version.

**Verify:** update `tests/health.test.js`'s existing "reports app and binary versions"
test to additionally assert that a non-owner JWT (`userId` other than the owner's, as
`tests/accountsSettings.test.js:297`'s `other()` helper already mints) gets
`binaries.ytDlp.version === null`, `binaries.ffmpeg.version === null`, `node === null`,
while `binaries.ytDlp.available`/`cache`/`platform` are unchanged; keep the existing
owner-id (`userId: 1`) test case passing unmodified (it should still see full detail).

**Size:** S (under an hour).

### 3.3 `generic-error-handler-masks-status-codes` — info — **confirmed**, worth fixing

**Location:** `app.js:237-244` (central error handler).

Verified: the handler only special-cases the CORS rejection message; every other error —
including body-parser's `entity.too.large` (413) and `entity.parse.failed` (400), both of
which already carry a safe `err.status`/`err.statusCode` and no internal detail — is
answered with a flat `500`. Not an information leak (confirmed no stack trace/path ever
reaches the client either way), but it makes client errors look like server errors in logs
and any uptime/error-rate monitoring.

**Fix:** `app.js`, central error handler:

```js
app.use((err, req, res, next) => {
    if (err && err.message === 'Not allowed by CORS') {
        return res.status(403).json({ error: 'Origin not allowed' });
    }
    console.error('Unhandled error:', err);
    if (res.headersSent) return;
    const status = Number(err && (err.status || err.statusCode));
    if (status >= 400 && status < 500) {
        return res.status(status).json({ error: status === 413 ? 'Request body too large.' : 'Malformed request.' });
    }
    res.status(500).json({ error: 'Internal server error' });
});
```

**Verify:** add to an `app.js`-level test (or extend an existing body-limit test): a
~2 MB `POST /api/register` body now returns `413` (not `500`) with
`{"error":"Request body too large."}`; a malformed-JSON body now returns `400` (not `500`)
with `{"error":"Malformed request."}`; existing tests that only check for "no stack trace
in the response" continue to pass since the message stays generic.

**Size:** S (under an hour). Risk: double-check no test currently asserts `500` for these
two cases specifically (grep for `entity.too.large`/oversized-body tests before changing);
if one does, update it alongside this fix.

## 4. Broader improvements (not flagged by the Exploiter)

- **Shared SSRF guard module.** Once `services/netGuard.js` exists for fix 3.1, consider
  also routing `services/lyrics` or any other outbound-URL fetch the app adds in the
  future through it by default, so new code doesn't have to remember to reinvent the
  blocklist.
- **`cloud/client.js` transport.** As noted in 3.1's follow-up, migrating off global
  `fetch()` to core `https.request()`/`http.request()` with a pinned `lookup` would also
  let `MAX_RESPONSE_BYTES` enforcement and the 15 s timeout be expressed the same way as
  `artworkColors.js`'s `downloadWith`, reducing the number of distinct "fetch a URL safely"
  patterns in the codebase from two to one.
- **Dev-dependency hygiene.** The 18 `npm audit` findings (all transitive Jest-toolchain
  dev dependencies — `jest`, `glob`, `deepmerge`, etc.) are not reachable from production
  code, but a routine `npm update` / `npm audit fix` pass in a maintenance window would
  clear them without touching runtime behavior; no urgency.
- **`/api/health` test coverage for ownership.** Beyond the fix in 3.2, consider adding a
  `tests/health.test.js` case that documents *why* the endpoint stays reachable by
  non-owners (so a future contributor doesn't "fix" it by adding `requireOwner` and
  silently break `SystemPanel.jsx`/`MusicContext.jsx` for non-owner accounts).
