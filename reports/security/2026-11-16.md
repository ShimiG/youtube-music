# Security exploitation report — 2026-11-16

## 1. Summary

- Tested the local instance's authentication/authorization, injection, path-traversal, SSRF, rate-limiting and info-disclosure surface against `http://localhost:3999`, booted from this checkout with a throwaway `JWT_SECRET`, an isolated `MUSIC_DATA_DIR`, and no SoundCloud/yt-dlp credentials (fully offline).
- Ran `npm audit` at the repo root and in `client/`, and re-read the main request-handling code paths (`app.js`, middleware, every controller that touches the database, the filesystem, or spawns `yt-dlp`/`ffmpeg`).
- Results: **0 confirmed**, **2 potential**, **6 attempted-failed** (attacks the app correctly defended), **3 info** (hardening notes / dependency summary).
- The single most urgent item is **potential**, not confirmed: `PUT /api/cloud/url` (owner-only) has the server make an outbound HTTP request to an arbitrary attacker/owner-supplied URL with no private-network/metadata-address guard, unlike the equivalent, well-guarded code in `services/artworkColors.js`. Recommend adding the same IP-blocklist pattern there.
- Good news: a previously **confirmed** high-impact finding from the 2026-11-09 run — `/stream` and `/duration` being reachable with no authentication at all, letting any web page a user visits trigger `yt-dlp`/`ffmpeg` transcodes — is now fixed by a short-lived, purpose-pinned media token (`GET /api/media/token` + `requireMediaToken`), and was re-verified as fixed in this run.

## 2. Assumptions

- Base URL: `http://localhost:3999` (as instructed). Booted with `PORT=3999`, `HOST=127.0.0.1`, a freshly generated 64-hex-char `JWT_SECRET`, `MUSIC_DATA_DIR` pointed at a scratch directory (never the real per-user data folder), `YTDLP_AUTO_UPDATE=false`, and `SOUNDCLOUD_CLIENT_ID`/`SECRET` left unset.
- `yt-dlp` is not installed in this sandbox (`which yt-dlp` found nothing); `ffmpeg` is available (`/usr/bin/ffmpeg`, and the bundled `ffmpeg-static` binary). This means every YouTube/SoundCloud-yt-dlp-fallback play attempt fails fast with `spawn yt-dlp ENOENT` before any network or filesystem work — expected and does not weaken the path-traversal/injection coverage, since those checks run before the process spawn.
- Registered two throwaway local accounts: `exploiter_alice` (user id 1, so she is the installation "owner" for `requireOwner`-gated routes) and `exploiter_bob` (user id 2, non-owner). A third account, `a' OR '1'='1`, was registered deliberately as a SQL-injection-style username to prove it is stored and queried as a literal string.
- Google OAuth, SoundCloud OAuth, and cloud-sync flows that would need to reach `accounts.google.com`, `api.soundcloud.com`, or a real cloud backend were **not** exercised end-to-end (out of scope: third-party/remote hosts). Where this mattered, the specific gap is called out below as `skipped`.
- A planned SSRF probe against a cloud-metadata-style address (`169.254.169.254`) was not run dynamically: the test harness's own safety classifier declined that request. That part of the `cloud-url-no-ssrf-guard` finding is therefore `potential` (code review + a loopback-only dynamic probe), not `confirmed`.
- `npm audit` needed one retry at the repo root after a transient tool-classifier rejection; the client audit ran on the first try. Both are ordinary dependency-vulnerability-database lookups, not attacks on a third party.

## 3. Confirmed vulnerabilities

None. Every exploit attempted in this run was either correctly defended (see §5) or could only be partially verified and is reported as potential (see §4).

## 4. Potential weaknesses

### 4.1 `cloud-url-no-ssrf-guard` — medium — SSRF, owner-gated

**Location:** `services/cloud/sync.js:80-102` (`checkCloudUrl`, `saveCloudUrl`), `controllers/cloudController.js:43-48` (`saveUrl`).

`PUT /api/cloud/url` (behind `requireAuth` + `settingsController.requireOwner`, so only the first local account on the installation can call it) takes a URL from the request body and has the server issue an HTTP GET to `<url>/health` to check whether it looks like a Music Manager cloud instance, before anything is saved or any further confirmation is required. Contrast this with `services/artworkColors.js`, which guards every outbound image fetch with a `net.BlockList` covering loopback, RFC1918, link-local/CGNAT and IPv6-mapped-IPv4 ranges, checked on the exact address the socket connects to (no DNS-rebinding window). No equivalent guard was found for the cloud URL path.

**Exploit attempted:** as the owner account, `PUT /api/cloud/url {"url":"http://127.0.0.1:3999"}` (pointed at the test instance's own loopback port, to stay strictly local) returned:

```
HTTP/1.1 400 Bad Request
{"error":"That address answered, but it is not a Music Manager cloud service.","code":"CLOUD_BAD_URL"}
```

This proves the server actually connected to and read a response from the loopback address — there was no "that address is not allowed" rejection *before* the request was made, which is exactly the behavior a pre-connect IP blocklist would have produced instead (as it does for artwork URLs). A further probe against `169.254.169.254` (the common cloud-provider metadata address, which would be a stronger demonstration of impact) was declined by the test harness's own safety classifier and was not run.

**Impact:** scoped to whoever controls the owner account. If an owner's account is otherwise compromised (e.g. a stolen session token, or a future bug elsewhere that lets a non-owner become "owner"), this becomes a way to make the server probe or interact with internal-network services and metadata endpoints, with the oracle (`CLOUD_BAD_URL` vs. an unreachable-style error) leaking whether something answered at that address. It is not exploitable by an arbitrary unauthenticated or non-owner user today.

### 4.2 `health-endpoint-any-authenticated-user` — low — info-disclosure

**Location:** `app.js:90-96`.

The code comment for `GET /api/health` says it is "Behind our login because binary versions help an attacker pick a known exploit." That correctly blocks unauthenticated access, but the bar used is only `requireAuth`, not `requireOwner` (unlike `/api/settings/services` and `/api/system/log`, which are owner-only). On an installation with more than one local account, any registered user — not just the trusted first/owner account — can read exact `yt-dlp`/`ffmpeg`/Node versions, platform, and cache stats.

**Evidence:** as `exploiter_bob` (second-registered, non-owner), `GET /api/health` returned `200` with full binary-version detail, while `PUT /api/settings/services/youtube` and `GET /api/system/log` both correctly returned `403 SETTINGS_OWNER_ONLY` for the same account.

This may be an intentional design choice (every local account on a single-user desktop app is assumed equally trusted), so it is reported as a low-severity potential gap rather than a confirmed bug.

## 5. Successfully defended

All of the following were attempted against the live local instance and correctly blocked; see `reports/security/2026-11-16.findings.json` for the full evidence text of each.

- **Authentication / JWT handling** (`jwt-verify-no-algorithm-pin`): no-token, `alg=none` forged token, HS256-with-wrong-secret forged token, expired token, token with no `exp` claim, `x-user-id` header spoofing attempt, and purpose-confusion in both directions (a media token presented as a session token, and a session token presented where a media token is required) were all rejected with `401`.
- **Previously-confirmed DoS now fixed** (`media-endpoints-unauthenticated-transcode-dos`): `/stream` and `/duration` now require a short-lived, purpose-pinned media token minted only via an authenticated `GET /api/media/token`; both routes correctly return `401 MEDIA_TOKEN_REQUIRED` with no token, and a session JWT used in place of a media token is also rejected.
- **IDOR / cross-user access** (`idor-playlists-history-attempted`): a second account could not read or write the first account's custom playlist (`404 Playlist not found` on both GET and POST), and each account's `/history` and `/api/custom-playlists` only ever showed its own data.
- **Path traversal / argument injection** (`stream-path-traversal-attempted`): `videoId=../../../../etc/passwd` (both `source=youtube` and `source=local`), shell-metacharacter payloads (`;id;`, `$(id)`) in `videoId`, and out-of-range/non-numeric `seek` values were all rejected with `400` before any process could be spawned or any path resolved outside the cache/media directories. Adding a local music folder at `/etc`, `/`, or via a `~/../../../../etc` traversal was rejected with `400 LOCAL_NOT_ALLOWED`.
- **SQL injection** (`sql-injection-attempted`): a SQL-injection-style username registered successfully only as a literal string (verified by a subsequent clean login); a `DROP TABLE`-style `trackId` was stored and later read back as literal text with no effect on the schema; a SQL-injection-style `:source` path segment was rejected with `400 SOURCE_UNKNOWN` before reaching any query.
- **Reflected XSS** (`reflected-xss-search-query-attempted`): a `<script>` payload in a search `q` parameter only ever reached a `Content-Type: application/json` response with `X-Content-Type-Options: nosniff`; no HTML was returned at any point.
- **SSRF via artwork cover URLs**: internal/loopback IP literals, IPv6 loopback, plain `http://`, and credentials-in-URL were all rejected (`{"status":"none"}` or `400 Only plain https image URLs are accepted.`) before any DNS lookup or connection was attempted for the blocked cases.
- **SSRF via the SoundCloud pagination cursor**: `buildUrl()` resolves every cursor against the fixed API origin and rejects anything that does not stay on `https://api.soundcloud.com` — re-confirmed by code review (same fix verified dynamically in the 2026-11-09 run).
- **CORS**: an unlisted `Origin` got `403 Forbidden` with no `Access-Control-Allow-Origin` header; an allowlisted origin got the header back correctly.
- **Rate limiting**: `POST /api/login` tripped the 20-per-15-minutes auth limiter (`429` once the shared register/login quota was exhausted); `GET /duration` tripped the 60-per-minute media limiter exactly at the configured threshold.
- **Owner-only settings**: a non-owner account got `403 SETTINGS_OWNER_ONLY` on both `PUT /api/settings/services/:source` and `GET /api/system/log`; the owner account could read the log, which contained no raw passwords, JWTs, or OAuth tokens (redacted by `services/logFile.js`).
- **OAuth callback input validation**: `GET /auth/google/callback` and `GET /auth/soundcloud/callback` both reject missing `code`/`state` and a `state` signed with the wrong secret or wrong `purpose`, with `400`, before any call to Google or SoundCloud.
- **Request body limits**: a ~2 MB JSON body against `POST /api/register` (over the 1 MB `express.json` limit) was rejected (see §6 for the status-code nuance) with no stack trace or internal detail in the response.

## 6. Dependency and static findings

- **Root `npm audit`**: 18 findings, all low/moderate, every one a transitive dev dependency of the Jest test toolchain (`jest`, `@jest/*`, `babel-jest`, `glob`, `deepmerge`, `test-exclude`, …). None are reachable from the production dependency list in `package.json` (`express`, `jsonwebtoken`, `bcryptjs`, `helmet`, `cors`, `express-rate-limit`, `@googleapis/youtube`, `ffmpeg-static`, `music-metadata`, `dotenv`).
- **`client/` `npm audit`**: 0 findings at any severity.
- **Code review, no dynamic exploit needed**: every `child_process.execFile`/`spawn` call in the codebase (`yt-dlp`, `ffmpeg`) passes an argument array with no shell, so there is no shell-metacharacter injection surface even before the input-validation layer is reached. All SQL access goes through parameterized `?` placeholders; the two `${...}`-interpolated SQL strings found (`config/db.js`'s migration helper, `services/tokenCrypto.js`) only ever interpolate hard-coded table/column name constants, never request data.
- **Central error handler** (`app.js:237-244`) always answers client errors (oversized body, malformed JSON) with a flat `500` instead of forwarding the originating error's own `400`/`413` status — confirmed by comparing the HTTP response to the server-log detail for both cases. This is a monitoring/response-accuracy nit, not an information leak (no stack trace or internal path ever reached the client in either case) — see `generic-error-handler-masks-status-codes` in the findings file.
- **Tauri shell CSP** (`src-tauri/tauri.conf.json`): still a strict, non-null CSP with no `unsafe-eval`, and the shell allowlist has no `execute` entry — static-only check, out of scope for the HTTP instance under test, re-confirmed unchanged from the 2026-11-08/09 reports.

## 7. Scope and safety

- Every request in this run was sent to `http://127.0.0.1:3999`, a disposable instance of this repository's own code, started and stopped entirely within this session.
- No request was sent to any third-party host, API, or production system. SoundCloud, Google OAuth, and cloud-sync end-to-end flows that would reach a real remote service were not exercised; where that limited a check, it is called out explicitly (see §2, and the `cloud-url-no-ssrf-guard` finding).
- No application source files were modified to perform this testing (only environment variables at boot). `git status --porcelain` shows a clean working tree except for the two new report files this run produced.
- All throwaway accounts, playlists, history rows, and the isolated `MUSIC_DATA_DIR` (including its generated `.jwt-secret`/`.token-key` and SQLite database) lived under a scratch directory outside the repository and were deleted before finishing. The server process was terminated at the end of testing.
